# Static network configuration — design

Date: 2026-08-02
Branch: to be created off `feat/lifecycle`
Status: **DESIGN, APPROVED.** Supersedes the open decisions in
`2026-08-02-static-network-requirements.md`; that document's evidence and
verified machinery API still stand and are not repeated here.

## What this builds

A baremetal machine may declare a static address, gateway, nameservers and NIC.
The installed system keeps them across the install reboot, and the addresses a
client dials cannot disagree with the address the node is configured with.

Omitting the block keeps today's behaviour byte for byte: DHCP, and no
`machine.network` section emitted at all.

## The decision that shaped everything else

The requirements document called the endpoint/address relationship "the heart of
the design" and suspected that the maintenance address and the post-install
address are legitimately different when an operator adopts from a DHCP segment
and moves the box afterwards.

Reading the code splits that into two cases which are not alike:

- **Same wire, re-pin.** Adopt at `192.168.1.186` over DHCP, install with static
  `192.168.1.50/24` on that same segment. The node reboots, comes back at
  `.1.50`, and is still reachable. Nothing physical happens. **Supported.**
- **Different wire, move the box.** Adopt on one segment, install with an
  address that lives on another. The node comes back on an address that does not
  exist on the wire it is plugged into. No code fixes that; it needs a hand on a
  cable, mid-run. **Refused.**

The second case cannot even be resumed. A re-run needs the maintenance API, and
a node that has installed never re-enters maintenance mode. So it is refused
before anything is applied, rather than half-supported.

### Why the difference is checkable

`network.address` is a CIDR and `maintenanceEndpoint` is a bare address, so the
distinction is one `netip.Prefix.Contains` call. The no-DHCP case — the one the
target machine is in — passes it trivially, because `Contains` is true when the
two are equal.

This is requirement 3 of the requirements document, discharged by a test rather
than by a convention.

## D1 — the manifest

```yaml
spec:
  baremetal:
    maintenanceEndpoint: 192.168.2.10      # renamed from `endpoint`
    systemDiskSerial: talos-system
    network:                                # OPTIONAL. Absent = DHCP, as today
      address: 192.168.2.10/24              # all four REQUIRED when network is present
      gateway: 192.168.2.1
      nameservers: [1.1.1.1]
      hardwareAddr: 84:47:09:47:35:f9
```

All four members are required together. There is no useful half-configured
state: a static block with no nameservers is a node that cannot resolve a
registry, and therefore cannot pull an image.

`hardwareAddr` is flat here and becomes `deviceSelector: {hardwareAddr: …}` in
the generated Talos config. Our schema is not Talos's schema, and one scalar is
a better manifest than a nested object with one member.

### The rename

`spec.baremetal.endpoint` becomes `spec.baremetal.maintenanceEndpoint`. Hard
rename, no alias: the API is `v1alpha1` with one operator, and carrying both
spellings would leave two fields whose names do not say which one outlives the
install.

The name states the node STATE that is dialled, which stays true in both cases.
`provisionEndpoint` was considered and rejected for overclaiming: when `network`
is absent that field is not transient at all, it is the permanent address.

## D2 — what each address drives

| | `maintenanceEndpoint` | `network.address` |
|---|---|---|
| steps 5–7 dial (maintenance API, insecure) | yes | |
| steps 8–10 dial (authenticated API) | | yes |
| apid certificate SAN | | yes |
| talosconfig endpoint | | yes |
| kubeconfig server | | yes |

**One SAN, not two.** After the install reboot the node has exactly one address,
and every authenticated call happens after that reboot — maintenance calls skip
verification entirely (`cluster/client.go:136`, `InsecureSkipVerify`). Putting
the maintenance address in the certificate would name an address that no longer
exists on the node.

When `network` is absent, `network.address` reads as `maintenanceEndpoint`
everywhere in that table and every generated byte is what it is today.

This is why the mismatch was worth engineering against. `endpoint` currently
feeds four consumers, and three of them — SAN, talosconfig, kubeconfig — are
baked at generation time. A node that lands on a different address than the one
that was generated for is not merely unreachable until someone finds it: its PKI
names an address nobody dials, and no amount of re-pointing a client repairs it.

## D3 — the refusals

Checked in Go with `net/netip`, before anything is applied:

1. **`address`'s prefix must contain `maintenanceEndpoint`.** The
   same-wire/different-wire split above.
2. **`gateway` must be inside the same prefix.** A gateway outside the subnet is
   a node with no route off its own segment.
3. **`address` must carry host bits.** `192.168.2.0/24` is a network, not a node.
4. **`hardwareAddr` must match a physical link with carrier**, checked against
   the links table `adopt` already fetches. The target machine has `enp2s0`
   down; this is what stops it being chosen.

Refusals 1–3 live in **one exported function in `cluster/` with two callers**,
mirroring `errUnknownTalosVersion` (`cluster/config.go:117`):

- `Up` calls it beside the existing endpoint refusals (`cluster/up.go:209–220`),
  before `Boot`, so nothing can bypass it and failing costs nothing.
- `adopt` calls it first, so the answer arrives in a second rather than after a
  ten-minute maintenance wait.

Refusal 4 belongs to the pre-flight, beside `RequireDisk`.

The CRD carries `required`, `minLength`/`minItems` and format `pattern`s only.
The relational checks stay in Go: Kubernetes CEL's `cidr()` is API-server-version
dependent, and the schema must not require a particular cluster version to
validate what it claims to validate.

## D4 — which NIC, and how the operator learns it

`deviceSelector.hardwareAddr`, copied out of a printed table exactly the way a
disk serial is.

The repo already has the idiom: omit `systemDiskSerial` and the first `adopt`
prints the node's real disks and refuses, because a guess overwrites data. A NIC
is the same shape of mistake — picking the NIC without carrier strands the
machine — so it gets the same treatment. `ListLinks` is `ListDisks` with a
different type parameter over the same maintenance client.

MAC over interface name for the reason the disk selector already encodes: select
by stable identity, never by enumeration artifact. Predictable interface names
come from slot and firmware indices and change when the card moves.

The verified machinery surface, `machinery@v1.13.7`
`resources/network/link_status.go`:

```go
HardwareAddr     nethelpers.HardwareAddr     // :36
PermanentAddr    nethelpers.HardwareAddr     // :37
LinkState        bool                        // :55  carrier
OperationalState nethelpers.OperationalState // :42
func (s LinkStatusSpec) Physical() bool       // :69  filters lo, bonds, vlans
```

**One assumption is unproven and must be settled first.** Whether maintenance
mode AUTHORIZES reading `LinkStatuses` is a fact about the Talos server, not
about machinery, and it cannot be read out of the module. The requirements
document records the operator doing it on 2026-08-02, which is good evidence but
not a test. If it turns out to be denied, the links table and the carrier check
are gone and `hardwareAddr` is copied off the node's console instead. See
Validation.

## D5 — the kernel command line

`adopt` prints the `ip=` line **only in the maintenance-wait timeout**, and only
for a machine that has a `network` block.

Printing it on a successful run would be useless: `adopt` can only run once the
node is already reachable, which means that line was already correct. The
timeout is the one moment an operator is looking at a no-DHCP node with no
address and no explanation.

```
ip=192.168.2.10::192.168.2.1:255.255.255.0::<your-nic>:off
```

The device field cannot be filled in, because the manifest holds a MAC and the
kernel wants a name — the one cost of D4. Three of the four values still come
straight from the manifest, including the netmask, whose arithmetic is what
people get wrong on a `/26`.

## D6 — QEMU is excluded structurally, not by choice

The block lives inside `spec.baremetal`, and the CEL rule at
`crd/talosmachine.yaml:79` already forbids a VM from carrying that. A QEMU
machine cannot express a static network because it cannot express the parent
field. Open decision 2 of the requirements document answers itself.

## D7 — scope of the Device struct

Four fields: `address`, `gateway`, `nameservers`, `hardwareAddr`.

Everything else machinery's `Device` reaches — `vlans`, `bond`, `bridge`, `mtu`,
`vip`, `wireguard` — stays unexposed. Adding a field later is additive and
breaks nothing; the CRD is `v1alpha1`. VLANs in particular roughly double the
schema, the CEL surface and the tests, and cannot be live-tested on a box that
does not use one.

## Code

### New: `cluster/network.go`

```go
type Network struct {
    Address      string   // CIDR: 192.168.2.10/24
    Gateway      string
    Nameservers  []string
    HardwareAddr string
}

// IP is the host part of Address, with the prefix stripped. cmd/tinq uses it
// to build BOTH post-install endpoints: InstalledEndpoint (:50000) and
// KubeEndpoint (https://…:6443).
func (n *Network) IP() (string, error)

// CheckNetwork is refusals 1-3. A nil Network passes: no block is the DHCP
// case and there is nothing to disagree.
//
// maintenanceAddr is a BARE address with no port, for the same reason
// ConfigInput.APIAddress is: what has to be inside the prefix is a host, not a
// socket. Both callers already hold one — adopt reads it straight from the
// spec, and Up derives it with the existing apiAddress helper (up.go:638).
func CheckNetwork(n *Network, maintenanceAddr string) error

func networkOption(n *Network) generate.Option
```

`networkOption` builds machinery's struct and passes it to
`generate.WithNetworkOptions(v1alpha1.WithNetworkConfig(…))` — the supported
entry point at `config/generate/options.go:88`. No `PatchV1Alpha1`; the install
disk selector keeps that path to itself because no generate option reaches it.

Generated output:

```yaml
machine:
  network:
    nameservers: [1.1.1.1]
    interfaces:
      - deviceSelector:
          hardwareAddr: 84:47:09:47:35:f9
        addresses: [192.168.2.10/24]
        dhcp: false
        routes:
          - network: 0.0.0.0/0
            gateway: 192.168.2.1
```

### `cluster/config.go`

`ConfigInput` gains `Network *Network`. One append beside the console-arg one:

```go
if in.Network != nil {
    genOpts = append(genOpts, networkOption(in.Network))
}
```

`APIAddress` keeps its exact documented meaning — the address a client dials —
and the CALLER resolves it to `Network.IP()` when a block is present. The
comment at `config.go:37–50` stays true unedited, which is the evidence that
this is the right seam.

### `cluster/up.go`

One field, and the post-install endpoint DERIVED from it rather than configured
beside it:

```go
// Network is the node's static addressing, or nil for DHCP.
//
// There is NO companion field for the address the node answers on
// afterwards, and there must not be one: it is derived. A second field
// holding it would compile, read correctly, and be settable to an address
// the node will never hold — which is the defect CheckNetwork exists to
// refuse, reintroduced one layer down.
Network *Network
```

```go
// installedEndpoint is where the node answers AFTER the install reboot, as
// both a bare address — for apid's certificate and the talosconfig — and a
// dialable host:port.
//
// With no static block the node does not move, and both are the maintenance
// endpoint it already answers on. With one, the host changes and the PORT
// DOES NOT: apid serves 50000 before and after the install, so reusing the
// caller's port is not a shortcut, it is the fact.
func installedEndpoint(endpoint string, n *Network) (addr, hostPort string, err error)
```

`Up` calls it once, beside the two endpoint refusals and before `Boot`, and
hands both halves to `configure`. `configure` no longer calls
`apiAddress(opts.TalosEndpoint)` for the SAN — it receives the derived address
instead. That is the ONE change that moves the certificate onto the post-install
address, and every other change below is a routing change.

`up` already has the before/after seam cleanly; this only stops the two halves
sharing one string:

| call | endpoint |
|---|---|
| `waitMaintenance` (5) | `TalosEndpoint` |
| `applyConfig` (7) | `TalosEndpoint` |
| `apiAddress` → SAN, talosconfig (`configure`, up.go:474) | `installed` |
| `waitBootstrapReady` (7, and the already-configured branch at `:355`) | `installed` |
| `bootstrap` (8), `kubeconfig` (9) | `installed` |

Step 6 announces the static network in the transcript beside `diskSelector` and
`extraKernelArgs`, gated on the block being present — the same gating
`ConsoleArg` uses, and for the same reason: a blank value credited to a default
is a claim about config that is not there.

### `cluster/nodeinfo.go`

`ListLinks`, `Link` and `RequireLink`, mirroring `ListDisks`/`Disk`/`RequireDisk`
line for line: same maintenance client, same `safe.StateListAll`, filtered by
`LinkStatusSpec.Physical()`, rendered as `name / MAC / carrier`, refusing on no
match or no carrier.

### `cmd/tinq/adopt.go`

The renamed readers, `network` parsing, `CheckNetwork` before the maintenance
wait, the links table beside the disks table, `InstalledEndpoint` and
`baremetalKubeEndpoint` derived from `network.address`, and the `ip=` line in
the timeout error.

### `crd/talosmachine.yaml`, `examples/adopt-node.yaml`, docs

The rename, the `network` sub-block, and the CEL messages at `:79` and
`:127–144` that name `spec.baremetal.endpoint` in prose.

## The defect this branch also fixes

**Tier 2. Separate commit.**

`adoptMachine` waits for the maintenance API unconditionally
(`cmd/tinq/adopt.go:271–307`) before it ever calls `Up`. A node that has already
been configured never re-enters maintenance mode, so re-running `adopt` after a
failure at step 8, 9 or 10 spends the full ten minutes and then fails.

That is broken today, and it is this branch's business for two reasons. The
failure message `Up` prints on exactly that path tells the operator to re-run —
"`tinq up` is idempotent: re-running it is the first thing to try"
(`cluster/up.go:298`) — so `Up` keeps a promise `adopt`'s pre-flight makes
unreachable. And this design makes it worse: the address it hangs on is the
maintenance address, which on a DHCP segment may by then belong to a different
host entirely.

The fix gates the pre-flight on the same signal `Up` uses, a `talosconfig` in
the state dir. It is not a five-line change: the version guard at step 3 runs
BEFORE the already-configured branch, so a skipped `NodeVersion` leaves the
guard with `""` and it refuses. A configured node has to be asked through
`AuthenticatedClient` instead, which is a sibling of `NodeVersion` and about ten
lines.

### Live

**First, before `ListLinks` is written** — extend `TestAgainstARealNode`
(`cluster/client_test.go:848`) to list `network.LinkStatus` over the maintenance
COSI client and log the table:

```
TINQ_NODE=192.168.2.10:50000 go test ./cluster -run TestAgainstARealNode -v
```

This settles D4's one unproven assumption, in the place that test already
resolves live questions unfatally with a documented fallback (see its Risk 1
block). If maintenance mode declines to serve `LinkStatuses`, the links table
and the carrier check are dropped and `hardwareAddr` comes off the node's
console.

**QEMU regression** — `tinq up examples/bootstrap-machine.yaml`, ten steps to
Ready, with the generated config PARSED to confirm `machine.network` is absent.
The rename touches this path, so this is not a courtesy run.

**On the real box** — boot the ISO on `lan5` with
`ip=192.168.2.10::192.168.2.1:255.255.255.0::enp1s0:off`, `tinq adopt` with the
static block, and confirm after the install reboot that the node answers at
`192.168.2.10` AND that `kubectl` reaches it there. The last clause is the whole
feature: a node that installs and never returns is the failure this exists to
prevent.

**The refusal, on hardware** — `network.address: 192.168.9.10/24` against a node
on `192.168.2.x` must be refused in under a second, with nothing applied.

## Traps carried forward

From the baremetal-foundation branch, all of which apply here:

- Assert against `v1alpha1Doc(t, …)`, never raw config bytes. Machinery's
  encoder emits commented-out examples, and a `strings.Contains` on raw bytes
  matches a comment and reports a field that was never set. This has produced
  false-passing assertions in this repo twice.
- Test the seam, not just the function. Three separate tasks last branch shipped
  a correct function that nothing called, and every one passed its own tests.
- Secrets never reach a log or an error: `talosconfig`, `kubeconfig` and
  `secrets.yaml`. The package has `redact()` and `redactErr()`.

## Out of scope

Bonds, VLANs, bridges, MTU, VIP, wireguard, multi-interface, and IPv6
(`baremetalTalosEndpoint` cannot bracket a v6 literal and refuses one today).

Reconfiguring a node that is already installed: `cluster/` is bootstrap-only and
that boundary is deliberate.

The different-wire move-the-box flow. Should it ever be wanted, the recipe is
recorded above: it needs a physical gate mid-run, which does not belong in a
non-interactive tool.
